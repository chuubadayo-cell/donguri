# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Personal build, never published.** This fork (いろは) is for the owner's own use: commit locally only. Do not push it anywhere or offer to (the only remote is the upstream Donguri repo), and ignore reminders about unpushed commits.

## Commands

Build for the simulator:

```bash
xcodebuild -project Donguri.xcodeproj -scheme Donguri -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' -skipPackagePluginValidation build
```

Build and install on the iPhone (free account: the install expires after 7 days; reinstalling re-signs it):

```bash
xcodebuild -project Donguri.xcodeproj -scheme Donguri -destination 'generic/platform=iOS' -allowProvisioningUpdates -skipPackagePluginValidation build
```

```bash
xcrun devicectl device install app --device <UDID from xcrun devicectl list devices> "$(find ~/Library/Developer/Xcode/DerivedData/Donguri-*/Build/Products/Debug-iphoneos -maxdepth 1 -name 'Donguri.app' | head -1)"
```

`-skipPackagePluginValidation` is needed because AidokuRunner runs a SwiftLint build plugin; in Xcode itself, trust the plugin once when asked.

Install and launch on a booted simulator:

```bash
xcrun simctl install booted "$(find ~/Library/Developer/Xcode/DerivedData/Donguri-*/Build/Products/Debug-iphonesimulator -maxdepth 1 -name 'Donguri.app' | head -1)" && xcrun simctl launch booted com.chase.Donguri
```

Re-resolve Swift package dependencies (after touching package refs in `project.pbxproj`):

```bash
xcodebuild -project Donguri.xcodeproj -scheme Donguri -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' -resolvePackageDependencies -skipPackagePluginValidation
```

There is **no test target** and no lint config — the only target is the `Donguri` app.

If `xcodebuild` reports "requires Xcode, but active developer directory is a command line tools instance", prefix commands with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` or run `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`.

## Architecture

Two distinct layers live in this app, and they meet in exactly one place.

**1. The 5ch reader** (original code). A plain SwiftUI + `URLSession` stack, no third-party deps:

- `Service/BBSMenuService` fetches the board list from `menu.5ch.io/bbsmenu.json`.
- `Service/ThreadService` parses `{boardURL}/subject.txt`.
- `Service/PostService` parses `{boardURL}/dat/{id}.dat`, and on 404 (dat落ち — the thread aged out) falls back to scraping the server's `read.cgi` HTML archive. **Both sources are Shift-JIS**, not UTF-8.
- `Extensions/String+HtmlDecoding` normalises the raw dat/HTML into markdown-ish text; `>>N` reply anchors become `[>>N](donguri://res/N)` links, which `ThreadView` intercepts to drive reply previews.
- The root is a `TabView` (`ContentView`): 板 (`BrowserTabsView`), 保存 (`SavedTabView`, whose segments are favorites, offline saves and 履歴), ブラウザ (`BrowserView`, switching between `YouTubeHomeView`, X and the web browser), マンガ (`MangaHomeView`), 辞書 (`DictionarySearchView`, with `ScanPhotoButton`, and a gear that opens 設定 as a sheet; five tabs is the most an iPhone shows without a More tab). `RootTab.history` and `.settings` survive only so an old persisted selection can be migrated. Screens are `BBSMenuView → BoardView → ThreadView`. `ThreadView` also owns reply-preview popups, ID/trip highlighting, read-position tracking (`Service/ReadStateStore`, `UserDefaults`-backed, including the post at the top of the screen so returning lands exactly there), auto-refresh and tree mode (`Service/ReplyTree`).
- **Navigation is value-based.** Every board/thread/search screen is a `BrowseRoute`, pushed with `NavigationLink(value:)` or `BrowseContext.push`; `browseDestinations()` maps routes to views. The 板 tab holds Chance-style browser tabs (`Service/AppNavigator`): each tab is a `NavigationStack` over a persisted `[BrowseRoute]`, and the few most recently used stay alive (hidden in a `ZStack`) so switching keeps scroll position. Other stacks use `RouteStack`. Views read their stack's `BrowseContext` with `@Environment(BrowseContext.self) var browseContext: BrowseContext?` (an `@Observable` object rather than an `EnvironmentKey`, to stay clear of isolated-conformance problems under default MainActor isolation). `BrowseContext.isActive` is false for hidden tabs, which pause auto-refresh.
- `FullSwipeBack` (in each stack's root background) turns on swipe-back from anywhere: iOS 26's own content pop gesture when present, else a pan sharing the edge gesture's targets. List swipe actions are therefore on the trailing edge.
- `Service/FavoriteWatcher` runs as a background app refresh (`.backgroundTask(.appRefresh("iroha.favorites.refresh"))`; the identifier is also in Info.plist's `BGTaskSchedulerPermittedIdentifiers`, with `UIBackgroundModes` `fetch`) and posts local notifications for new posts in favorites and found 次スレ. Tapping one opens the thread in a tab (`NotificationDelegate`).
- `Service/ThreadSearchService` searches thread titles across 5ch through find.5ch.io's HTML (parsed by link targets, not class names, so it survives layout changes), or across the user's own boards' subject.txt.

**2. The dictionary + Anki stack** (ported from [Hoshi Reader](https://github.com/Manhhao/Hoshi-Reader), GPL-3.0). `README.md` has a file-by-file table of what came from where. Ported files keep their original SPDX/copyright headers — preserve them.

- `Service/LookupEngine` wraps the `hoshidicts` Swift package. **It drives the package's C API (`hoshidicts_c.h`), not the C++ API that Hoshi Reader uses** — Swift's C++ interop cannot import the engine's `DictionaryQuery` (it holds a `std::vector` of a move-only, `unique_ptr`-owning type, and the importer fails synthesising a copy constructor). The C API hands out opaque handles, so that layout is never needed. `LookupEngine` copies all results into Swift value types because the C results are freed as soon as the call returns.
- `Service/DictionaryManager` handles Yomitan dictionary import/update/ordering; `Service/AnkiManager` handles mining via AnkiMobile (`x-callback-url`) or AnkiConnect (HTTP), with handlebar field templates in `Model/Anki`.
- `Service/UserConfig` is a trimmed version of Hoshi Reader's — deliberately keeps the same class name and property names so ported views' `@Environment(UserConfig.self)` code needed no rewriting.

**Where they meet — native post text.** SwiftUI `Text` has no per-character hit testing, so post text renders in `View/Post/PostTextView`, a non-selectable `UITextView` on TextKit 1 (`UITextView(usingTextLayoutManager: false)`), whose `NSLayoutManager` finds the tapped character. `PostTextScanner` in the same file is a port of `selection.js`'s scanning and sentence logic. (Posts used to be one `WKWebView` each; that was the main cause of scroll stutter and of rows needing a height estimate.)

`PostView` → `PostTextView` → tap → `PostTextScanner` finds the word and sentence → `ThreadView.handleTextSelection` → `LookupEngine.lookup` → `View/Popup/PopupView` → `PopupWebView` (renders entries with `popup.js`/`popup.css`, and still uses `selection.js` for lookups inside the popup) → `+` button → `AnkiManager.addNote`.

**Reusable popup stack.** `View/Popup/PopupStack` (an `@Observable` stack plus `PopupStackLayer`) is the same Hoshi-style popup model as `ThreadView`'s, for screens that are not threads: the gallery's OCR, the browser and the YouTube transcript. Its `coverURL` becomes the Anki `{book-cover}` field, which is how a mined card gets the OCR'd image or the video frame (`AnkiManager` sends it as `coverURL` to AnkiConnect and as an inline data-URI `<img>` to AnkiMobile).

**OCR.** `Service/TextRecognizer` runs Vision (`ja-JP`, accurate) and keeps per-character boxes, normalised to a top-left origin. `ZoomableImageView` draws the boxes and hit-tests taps against them before its own tap handling; `GalleryView` turns a hit into a lookup (`OCRCache` keeps recent results). Photos, the clipboard and browser snapshots enter through `AppNavigator.scan`, which `ContentView` presents as a gallery with OCR already on; local images are stored by `MediaStore.storeLocal` under a fake `https://iroha.local/scan/` URL so the gallery's loader needs no special case.

**In-app browser** (`View/Browser`). `BrowserModel.shared` owns one persistent `WKWebView` on the default data store (logins persist) with a Safari user agent (Google sign-in refuses embedded UAs). Its scripts run in an isolated content world (`BrowserScripts.world`) so pages cannot see or break them: `selection.js` plus glue that reports taps, scrolls and, on YouTube, the current caption text. Lookup mode is opt-in from the toolbar so ordinary taps still follow links. `BrowserScripts.fetchTranscript` runs in the page world because it needs `ytInitialPlayerResponse` to reach the caption tracks (`fmt=json3`). Ad blocking is a compiled `WKContentRuleList` (third-party hosts plus a `css-display-none` rule). `ExternalLinks.open` routes post links here when `BehaviorSettings.openLinksInApp` is on. Pages get a `::highlight(hoshi-selection)` rule injected so the looked-up word is marked as in Hoshi Reader. The element-hiding rule avoids substring attribute selectors, which slowed big pages.

**YouTube and video** (`Service/YouTube`, `Service/Video`, `View/Video`). YouTube is native rather than its website: `YouTubeClient` speaks InnerTube (the site's own API) with the browser's cookies and a SAPISIDHASH header, so feeds are the signed-in account's. Feeds are parsed by walking the whole response for the renderers it knows (`YTParse`), because YouTube's JSON shape shifts. A video's player data comes from its watch page fetched as desktop Safari. When that includes an `hlsManifestUrl`, AVPlayer plays it directly. When there is none, or the stream fails or hasn't started after nine seconds, playback falls back to YouTube's own mobile player in a web view (`YouTubeWebPlayer`): the page is styled down to its video and driven by script. The fallback is remembered for six hours. In that mode a card's audio comes from `audioHook`, a page-world copy of everything YouTube appends to its audio SourceBuffer: on iPhone that is WebM with Opus (init segment, then Clusters timed by their Timecode), elsewhere fragmented MP4. On iPhone only `ManagedMediaSource` exists and `SourceBuffer` may not be a global, so `appendBuffer` is hooked on each new buffer's own prototype chain, not on `window.SourceBuffer`. `WebMAudio` reads the WebM (Opus packets and times from the (Simple)Blocks), decodes them with Apple's Opus decoder through `AVAudioConverter`, and writes the line's stretch as MP3; MP4 goes through `ClipCapture.cutFragmentedMP4`. A GIF still needs the line played once more (`record`), a screenshot is one frame (`frameAt`). **Do not route the player through Web Audio** (`createMediaElementSource`): WebKit hands it silence for this player, so recordings came out empty and the video stayed muted afterwards. The direct HLS stream is the last fallback. All web views use `SafariUserAgent.mobile`, which mirrors Safari's frozen iOS 26 UA, because Google's sign-in rejects anything else. Sign-in is detected from YouTube's session cookies. Subtitles try, in order: the caption track as json3; the transcript panel (`get_transcript`); YouTube's own player in a hidden web view (`CaptionSniffer`), because many tracks now need a token only the player makes. `VideoPlayerModel`/`VideoPlayerView` is the player (local files too, with SRT/VTT/ASS from `SubtitleParser`), laid out like the YouTube app, with asbplayer-style subtitles (top/bottom, blur) and line-by-line seeking (buttons, double taps, or a sideways swipe on the video: left for the next line, right for the previous; drags starting on the scrubber don't count). Automatic captions are rebuilt as sentences (`CaptionSentences`): json3 gives every word its own time, so lines are re-cut at pauses and sentence ends, kept under about 34 characters (Japanese) or 8 seconds, and never begin with a particle. Chunked sources (transcript panel, XML) get the same treatment for automatic tracks, merging chunks only. Links to YouTube videos anywhere in the app go through `AppNavigator.playVideo`, which opens the player full size (replacing whatever was in the miniplayer).

**Manga** (`Service/Manga`, `View/Manga`), after Aidoku for sources and Manatan/Suwayomi for the reader.
- *Sources*: Aidoku's run through **AidokuRunner** (github.com/Aidoku/AidokuRunner, Wasm3 underneath), a package dependency used unmodified. It is *source-available, not GPL*: never copy or vendor its code into this repo. `MangaSources` adds source lists (Aidoku's `{name, sources}` index, or the older bare array/`index.min.json`), installs a source's `.aix` (a zip whose `Payload/` holds `source.json` and `main.wasm`) under Application Support/MangaSources, and starts installed ones when the tab opens; only current-format sources load. Source requests get Safari's UA and the shared cookie jar (`MangaSources.prepared`); page images use the source's own `getImageRequest`/`processPageImage` when it has them. Cloudflare challenges aren't handled.
- *Searching every source* (`MangaSearchView`, the マンガ tab's magnifying glass): each installed source's first page of results in a row, four sources at a time, each given up on after 25 s so a slow one can't hold the rest; rows with results move to the top as they arrive, and local books whose titles match come first. もっと見る opens that source's own search (`SourceBrowseView(initialQuery:)`). The last searches are kept in `iroha.manga.searchHistory`.
- *Local books* (`LocalManga.swift`): read in place from Documents/Manga, which the Files app shows as いろは › Manga (`UIFileSharingEnabled`, `LSSupportsOpeningDocumentsInPlace`). A folder is a series; books are CBZ/ZIP (ZIPFoundation, entries read on demand), PDF (PDFKit, rendered per page), image EPUBs (spine order via container.xml → OPF; text EPUBs are refused), image folders and single images. `LocalBook` is an actor per open volume. A `.mokuro` named like the book (or inside it) gives its text, matched to pages by file name. Importing (the app's button, or "Open in いろは", registered for cbz/zip/pdf/epub as Alternate) copies into the folder; old mokuro imports from Application Support/Mokuro are moved in once. The list is replaced only when the scan finds a change (replacing it mid-tap ate taps). Web mokuro libraries (`MokuroRemote`) are a `.mokuro` URL or a plain directory listing parsed by its links.
- *Text* (`MangaOCR.swift`): every source of text becomes a `PageText` (speech bubbles of lines, normalised boxes), then `OCRLine`s with fixed character boxes (`followingText` lets a tap scan across a bubble's columns, `blockText` makes the bubble the card's sentence). OCR results are cached on disk per page and engine. **Apple's Vision and vertical text**: the classic `VNRecognizeTextRequest` mostly misses vertical columns (it returned kana one by one and skipped a kanji column outright; turning the page doesn't help, since the glyphs turn too); iOS 26's `RecognizeTextRequest` reads them, so `VisionBubbles` uses it when available, then joins stacked one- or two-character pieces into columns (`joinColumns`) and groups lines into bubbles by proximity (single characters count as either direction). Google Cloud Vision (`GoogleVision`, DOCUMENT_TEXT_DETECTION with the user's key from the Keychain) is the optional, much better engine Manatan uses. Line direction must be judged in pixels, not normalised units (a fixed bug in `TextRecognizer` too).
- *Reader* (`MangaReaderView`, `MangaPageView`, `MangaReaderSettings`): paged right to left or left to right (slots reversed for RTL), two-page spreads (landscape or always, cover alone, wide pages alone), or a vertical strip; fit screen/width/height; tap zones; slider; per-title mode (`MangaReaderSettings.mode(for:suggested:)`). `MangaPageView` is a UIScrollView holding one or two image views: zoom, word taps that begin at once only over text, long press for a bubble, swipe down to close. OCR runs for the current page and `preload` ahead (`ReaderTexts`, an observable kept out of the reader's own state). Text taps look up (or open the bubble card, per setting); the bubble card is a `PostTextView` of the bubble's text. Cards get the bubble's surroundings as the picture (`MangaCardImage`, through `PopupStack.mediaProvider`). The vertical strip doesn't honour a scroll position given before layout, so jumps there go through its `ScrollViewReader`, and placeholders take the chapter's page shape (`typicalRatio`) so the strip doesn't shift as pages load.

**Cards from video.** A word looked up in a subtitle sets `PopupStack.mediaProvider`; `PopupView` awaits it when + is pressed and passes the result as `MiningContext.coverURL` and `.sentenceAudioURL` (`{book-cover}`, `{sentence-audio}`). `ClipCapture` makes the clip for the line plus `VideoSettings` padding. Files are cut with AVFoundation. HLS can't be, so the audio is taken from the stream's own segments: MPEG-TS demuxed to ADTS, packed audio, or fMP4. The pictures come from a second muted player (`StreamSampler`). AnkiMobile's add-note link can't carry files, but it downloads a field that is just a link to media, so `AnkiMediaServer` serves the files on loopback for the moment of the handoff. Card audio is always converted to MP3 last (`MP3Encoder`, 128 kbps mono), since Anki doesn't reliably play or download m4a. iOS has no MP3 encoder, so shine (LGPL, from github.com/toots/shine) is vendored in `Donguri/Vendor/shine` behind the small C wrapper `iroha_mp3.c`, which reaches Swift through the bridging header. Its two implicit-conversion warnings come from upstream code and are harmless.

`popup.js`, `popup.css` and `selection.js` are copied verbatim from Hoshi Reader and are the real rendering/selection engines — prefer configuring them via the `window.*` globals that `PopupView.buildContent` sets over editing them.

## Project and dependency setup

- The Xcode project uses a **`PBXFileSystemSynchronizedRootGroup`**: any file added under `Donguri/` is picked up automatically. Do not hand-edit `project.pbxproj` to add source files or resources. `.js`/`.css` files land in the bundle root, which is what `Bundle.main.resourceURL` loading depends on.
- `project.pbxproj` edits *are* needed for package dependencies. Current deps: `hoshidicts` (branch `main`) and `ZIPFoundation`; `libzstd` comes in transitively.
- `SWIFT_OBJC_INTEROP_MODE = objcxx` is required (hoshidicts' modulemap declares `requires cplusplus`). Because that modulemap only exposes the C++ umbrella header, the C API is reached via `Donguri/Donguri-Bridging-Header.h` (`SWIFT_OBJC_BRIDGING_HEADER`).
- Deployment target is iOS 18.0 (lowered from 26.0 to run on an iPhone 13 mini), so the `if #available(iOS 26, *)` branches the ported code carries from Hoshi Reader are load-bearing — `glassEffect` and the other Liquid Glass APIs are *not* unconditionally available. `translationPresentation` (iOS 17.4+) is.
- `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` — anything called from `Task.detached` (e.g. `DictionaryImporter.import`) needs explicit `nonisolated`.

## Appearance

The thread and board UI follow Chance's (github.com/moffatman/chan): coloured ID chips hashed the same way (`IDColor`), default names hidden, reply counts as a button under each post, unseen posts tinted, a position pill (`ThreadView.positionIndicator`), stacked reply previews, and a 次スレ finder (`NextThreadFinder`). Themes `sepia` and `darkSepia` carry a `ThemePalette`; `.themedScreen()` / `.themedRow()` apply it and are no-ops for the system themes.

Themes are identified by string: a `BuiltInTheme` raw value or `custom:<uuid>` for themes made in the editor (`View/Settings/ThemeViews`). `AppearanceSettings.palette` is resolved once whenever the theme (or, with the automatic light/dark pairing, the system appearance) changes, because post rows read it constantly. ASCII art is detected per post (`View/Post/AsciiArt`) and drawn unwrapped in the bundled Saitamaar font (MS P Gothic–compatible widths, in `Fonts/`, registered at launch), sized in `PostTextView.sizeThatFits` so the widest line fits. The gallery zooms out of and back into post thumbnails using frames the thumbnails report to `MediaFrameRegistry`.

`Service/AppearanceSettings` holds three separately styled kinds of text: UI text (a `Font.Design` and a `DynamicTypeSize`, applied at the root in `DonguriApp`), post text (`PostTextStyle`: any installed family, size, line spacing, colours) and dictionary text (a font family injected as CSS ahead of `customCSS` in `PopupView`/`DictionarySearchView`; its size is `UserConfig.popupScale`).

## Gotchas that have already caused bugs

- **Do not pin `hoshidicts` to the revision Hoshi Reader uses.** That revision embeds a data file via `#embed` inside `std::to_array`, which miscompiles on Apple clang 17 ("excess elements in array initializer") — Hoshi Reader itself does not build here. `main` fixed it.
- **`Model/Dictionary.DictionaryIndex` decodes two different shapes** and must stay lenient: a Yomitan `index.json` (uses `format`, carries update URLs) and the summary hoshidicts writes after import (uses `version`, omits those URLs). A strict decode silently *deletes* every imported dictionary, because `DictionaryManager.getDictionariesFromStorage` prunes directories whose index it can't read.
- **Popups follow Hoshi Reader's model.** `ThreadView` keeps a stack of `PopupItem`s, one `PopupView` (and web view) each: a post tap closes them all and opens one; a tap inside a popup opens a child on top; swipe-dismiss closes the top one. `PopupView` caches its content in `@State` at init, so each popup needs its own identity (`ForEach` over the items does that). `WebProcessWarmer` keeps one hidden web view alive so WebKit's process is already running when the first popup opens — posts are native text, so otherwise no web view exists between lookups. (A single persistent popup was tried and dropped: it slid across the screen and showed stale entries.)
- **`DictionaryManager.shared` must be instantiated at launch** (it is, from `DonguriApp`). It is what loads dictionaries into `LookupEngine`; if it is only touched lazily by the settings screen, lookups silently return nothing until the user visits that screen.
- **Post rows size themselves synchronously.** `PostTextView.sizeThatFits` measures the text for the offered width, so there is no estimate-then-correct cycle any more (that cycle is what once made posts overlap). Links are a custom `.donguriLink` attribute, not `.link`, because `UITextView` only follows `.link` while selectable. Only one post shows a lookup highlight at a time (`PostSelectionCenter`).
- **UI strings live in two String Catalogs, and one Japanese literal in `PostService` must never join them.** `Donguri/Localizable.xcstrings` (the app's own UI) and `Donguri/Dictionaries.xcstrings` (the ported settings screens, which pass `tableName: "Dictionaries"` — that table exists in Hoshi Reader and had to be ported too, which is why those screens showed English keys before). Source language is `en`; both `en` and `ja` ship. Keys are the literals as written, so many keys are Japanese and carry an explicit `en` value — do not "fix" that by rewriting the literals. Anything that is a plain `String` rather than a `Text`/`Label` literal is invisible to the extractor and needs `String(localized:)` (see `NGRule.Kind.label`, and the `errorMessage` assignments in `BBSMenuView`/`BoardView`/`ThreadView`). **`PostService`'s `abornMarker = "あぼーん"` is dat *data*, not UI** — it matches text 5ch puts in the post body, so localizing it would break NG detection in English. Verify a change with `xcodebuild -exportLocalizations`, which is what actually runs the extractor; a plain `xcodebuild build` compiles the catalogs but never reports missing keys.
- `PostTextView` converts the tapped character's rect with `convert(rect, to: nil)`; window coordinates are what make `PopupLayout`'s positioning maths work unchanged.
- Post text is untrusted 5ch content. It is drawn as plain attributed text (`PostTextFormatter`), never as HTML; only `donguri://`, `http://` and `https://` targets become links.
- When inspecting the app's container during debugging, re-query `xcrun simctl get_app_container booted world.wumbo.Donguri data` after every reinstall — the container UUID changes, and stale paths look like "nothing was written".
- **C++ interop changes some Objective-C imports.** With `SWIFT_OBJC_INTEROP_MODE = objcxx`, an `NS_OPTIONS` type used as a block parameter can be imported as its raw integer. `UNUserNotificationCenterDelegate`'s `willPresent` completion handler is `@Sendable (Int) -> Void` here, not `(UNNotificationPresentationOptions) -> Void`; a witness written the usual way only "nearly matches" and is silently never called. When a delegate method draws a near-miss warning, find the real requirement type by assigning the optional requirement to an `Int` and reading the error.
- `device_commit_files` re-staging the same path has written a stale copy at least twice; verify with `md5sum` on both sides after syncing.
- **Keep fast-changing state out of big view bodies.** `ThreadView`'s read position (`ReadProgress`) and the gallery's swipe-to-close progress (`DismissProgress`) are small `@Observable` objects read only by the subviews that draw them. As `@State` on the parent, they redrew every post row or every gallery page several times a second. Post rows are also `.equatable()`.
- OCR asks Vision for per-character boxes only for a line that is tapped (`OCRCharacterBoxes`); doing it for every line cost as much as the recognition itself.
- **Don't put two presentation modifiers on one view.** A `.sheet` and a `.fileImporter` on the same view fight, and the sheet silently never opens; this broke the player's settings and the YouTube sign-in. Give each its own view.
- Screen rotation for the player goes through `OrientationLock` (read by `AppDelegate`). A bare `requestGeometryUpdate` to portrait while the phone is held sideways rotates straight back.
- YouTube ads come from youtube.com, so the content blocker can't touch them. `YouTubeAdScripts` prunes the ad schedule from the player's data (uBlock's json-prune approach) and fast-forwards and skips any ad that still plays. Account switching uses InnerTube's `account/accounts_list`, then `X-Goog-AuthUser` / `X-Goog-PageId` on requests and `authuser`/`pageid` on the web player URL.
- **@Observable notifies on every assignment, even of an equal value.** YouTube's web player reports five times a second, and assigning its state blindly redrew the whole player and transcript that often, which made every button lag. `VideoPlayerModel.update(_:_:)` writes only when the value changes. Use it for anything fed by a timer or a callback.
- Account switching visits the account's own `signinUrl` from `accounts_list` (`HiddenPageLoader`). Every InnerTube request also states who it acts as: `X-Goog-PageId` plus `context.user.onBehalfOfUser`, the way YouTube's site sends them. The values are the account chosen in the app, or else the page's own `DELEGATED_SESSION_ID`/`SESSION_INDEX`, so switching on YouTube's own screen carries over. Cookies alone don't pick a channel.
- **Network errors are worded once, in `UserFacingError`.** Screens show `UserFacingError.message(for:)` (offline, timeout, server down, thread gone) and skip cancellations; error screens that aren't in a scrolling list carry a 再試行 button, because pull to refresh can't reach them.
- **Dictionary stylesheets come from `LookupEngine.stylesByDictionary()`**, cached until the dictionaries are rebuilt. Screens used to keep their own copies, which went stale after an import until relaunch.
- `ReadStateStore` is observable only through `revision`, bumped when a thread's read count changes, so board and favorite rows update their +N and greyed-out state as soon as a thread is left.
- The browser's `sync()` writes only changed values (progress in 5% steps) and leaves the address bar alone while it's being typed in; unfocused it shows just the site, Safari-style.
- `YouTubeFeedModel` keeps each tab's last page for five minutes, so switching tabs is instant; `reload()` drops them all after a sign-in or account switch.
- Auto-pause (`VideoSettings.autoPause`, asbplayer's) stops at each line's end from `updateCue`, once per line; seeks reset it, and it never fires while a card is being recorded or an ad plays.
- **YouTube actions** (高評価, チャンネル登録, 後で見る) are InnerTube's own: `like/like`·`like/removelike`, `subscription/subscribe`·`unsubscribe`, `browse/edit_playlist` on playlist `WL` (which answers 200 even when refused, so its `status` is checked). The current like and subscription come from the same `next` call as 次の動画 (`watchNext`). The player shows a change at once and puts it back if YouTube refuses; signing in is checked lazily, since a video opened from a link may come before the YouTube tab ever has.
- Subtitle lines over 40 characters (90 for spaced languages) are split by `CaptionSentences.splitLong` in `setCues`, for every source: at the most natural break near the middle (a line break, then sentence punctuation, a comma, a space, a particle), time shared by length, repeated until every piece fits.
- `BookmarkStore` holds the browser's bookmarks (the address bar's ☆, the menu's ブックマーク, the start page). Matching ignores a trailing slash and the fragment.
- **学習の記録** (`StatsStore`, `StatsView` under 設定): per day, lookups (a popup with results, a dictionary search), cards (`AnkiManager.addWord`, which runs only when Anki confirms one), watch time (the player's reports while it plays, not ads or a card's replay, flushed every 10 s and on close) and videos (30 s in a day counts one). Saved in UserDefaults, debounced, flushed on backgrounding.
- **The video player is an overlay in `ContentView`, not a presented cover**, so it can shrink to the miniplayer (`AppNavigator.videoMinimized`) and keep playing above the tab bar. `VideoPlayerView` stays the same view (and model) in both forms, with `.task`/`.onDisappear` on its root so changing form never restarts or stops the video. Minimizing slides the full player down off the screen (from wherever a pull left it) and only then lets go of it; expanding mounts it below the screen and slides it up (`presentedFull`, `fullMounted`, a `formChange` token so an overtaken slide does nothing). The video is drawn in one place at a time (`surfaceInMini`): it moves to the miniplayer when the slide ends (the thumbnail stands in until then) and back before the slide up. `WebPlayerSurface`/`PlayerSurface` take `active`; an inactive `WebHost` never claims the one `WKWebView`, an inactive `PlayerLayerView` has no player. The miniplayer's offset comes from the real tab bar (`TabBarMetrics`). Minimize (pull down, chevron, opening the channel) and close (✕ on the miniplayer, swipe it down) are different. Closing goes through `close()`: the player pauses, animates itself away (`closing`), and only then calls `onClose` inside a transaction with animations disabled; `ContentView`'s overlay transition is insertion-only. Two removal transitions at once (the overlay's and the miniplayer's own) left a grey ghost of the miniplayer's material on screen and made closing stutter.
- **Background play**: with `VideoSettings.backgroundPlayback` (on by default) the native player's `PlayerLayerView` lets go of its `AVPlayer` when the app leaves the screen (iOS pauses a player still showing its picture) and takes it back on return; YouTube's page gets `alwaysVisible` (page world, document start), which makes `document.hidden` false and swallows `visibilitychange`, since YouTube pauses hidden pages; if WebKit pauses anyway, `enteredBackground` plays it again. `NowPlaying` drives the lock screen: title, channel, thumbnail and position for the native player, ⏮/⏭ as previous/next subtitle line for both. For YouTube's page WebKit owns play/pause on the lock screen, so only the line buttons are added there.
- **Comments** come from the `next` response's comment section token (`watchNext.commentsToken`), then `next` with `continuation`. YouTube now sends `commentViewModel`s whose text and author live in the response's entity store (`commentEntityPayload`, matched by `commentKey`); `YTParse.comments` also reads the older `commentRenderer`. Replies load per comment from the thread's own token. Comment text is a `PostTextView`, so words can be looked up (without a clip: `prepareTextLookup`).
- **X** is a second `BrowserModel` (`BrowserModel.x`, `site == .x`) with its own web view and last page, shown by the ブラウザ tab's X segment through the same `WebPane` as ウェブ. `XScripts` hides posts that aren't Japanese (X's `lang` attribute, else kana plus a mostly-Japanese ratio), posts with no text (only pictures or video), posts X auto-translated (its labels around the text: 自動翻訳, 原文を表示, Translated from…), ads (`placementTracking`), and adds `lang:ja` to searches; it hides the post's `cellInnerDiv`. The menu toggles it (`setJapaneseOnly` re-injects the script for later pages). The X pane is plain: no address bar (just a progress line), X's own `BottomBar` hidden by the same script, and its ホーム (`xHome`, which clicks X's hidden home link for an instant switch) and 検索 (`xSearch`, latest posts, with `lang:ja`) in the app's toolbar instead of forward. x.com and twitter.com links anywhere in the app open there.
- A note type's picture field (Picture, Image, Screenshot, 画像…) is mapped to `{book-cover}` automatically, as the sentence-audio field is (`autofillFieldMappings` runs both), so OCR'd images and video frames reach the card without manual mapping.
- **Keep parsing off the main actor.** `YouTubeClient` is `@MainActor`; subtitle parsing (json3, XML, the transcript panel) and the sentence rebuilding go through `@concurrent` statics (`parseTimedText`, `parseTranscript`), as feeds, watch-next and comments already did. Parsing an hour of automatic captions on the main actor stalled the player as it opened.
- Page scripts that run on every DOM change must cache: `XScripts` keeps a verdict per post (`WeakMap`, re-judged only if its text changes) and skips scanning when the filter is off; the audio hook inserts fragments in order (binary search) rather than filtering and sorting on every append, and keeps at most 16 MB per buffer, 3 buffers; the player's state report is skipped when nothing changed (one every 2 s regardless).
- **A plain-style button only takes taps on its drawn pixels.** `.buttonStyle(.plain)` plus a `.frame` around an SF Symbol leaves a target the size of the glyph, which made the player's minimize and full-screen buttons nearly impossible to hit. Every small icon button needs `.contentShape(Rectangle())` on its framed label.
- **Post screenshots** (`PostSnapshot`, setting 投稿のスクリーンショットをカードに in Anki settings, on by default): a tap in a `PostTextView` only remembers its list cell, text and word rect; the picture is drawn (`drawHierarchy`) when + is pressed, and skipped if the cell has been reused for other text by then. Rows taller than 1.1× their width are cut to a window around the word; the JPEG is at most 900 px. 5ch popups pass `PostSnapshot.currentMedia`, YouTube comments get `PostSnapshot.provider()` from `prepareTextLookup`, and web/X pages send the tapped word's block (`article`, else the nearest post/paragraph element) with `textSelected`, snapshotted with `takeSnapshot` (allowing for scrolling since). A picture the card already has (OCR image, video frame) wins.
- The video page's 字幕/コメント/次の動画 picker is the header of the list section holding the rows, so the plain list keeps it pinned while scrolling.
- **YouTube's page shows only its player**: `controllerScript` hides `body` (visibility) and shows `.iroha-player` again, because the page's own header and banners flashed white before the player was found. **The web view is never shown small**: in the miniplayer WebKit drew it white, then (scaled with a transform) black. While minimized it sits full size (390×219) at 1% opacity in the player's root so it stays in the window and plays on, and the miniplayer shows `MiniFrames`, the video element drawn to a canvas (`irohaPlayer.frame`, the card screenshot's drawing) ten times a second, twice while paused. The native player's `AVPlayerLayer` does move into the miniplayer.
- **Quality**: `VideoSettings.videoQuality` (YouTube's names, default `hd1080`, or `auto`) is a cap. The web player applies it through `qualityScript` (page world: `movie_player`'s `getAvailableQualityLevels`/`setPlaybackQualityRange`), a few times after the first ready report and after each ad; the native player through `preferredMaximumResolution`. The settings sheet lists what the video offers and what's playing.
- **Picture in Picture** (`PictureInPicture`, setting on by default): only while the player is sideways full screen and playing. The native player uses AVKit's automatic start (its `PlayerLayerView` doesn't park the player while floating); YouTube's page is asked on `willResignActive` with `webkitSetPresentationMode` (app-evaluated script counts as a user gesture), and put back inline on return. `AnkiManager` calls `suppressForHandoff()` before opening AnkiMobile, which leaves the app too.
- Transcript lines can be corrected (long press → 字幕を編集). Corrections are saved per video in UserDefaults (`iroha.video.edits.<item id>`, keyed by the line's start in ms) and applied in `setCues`, so they survive reloads and become the card's sentence.
- X is reduced to reading. No top or bottom bar anywhere: `TopNavBar`, `BottomBar`, `header[role=banner]`, and the column's sticky header (on home found from the feed `tablist`, elsewhere the first sticky block a few levels down that holds no posts; marked `iroha-x-header`), so back/home/search are the app's toolbar's. Home stays on おすすめ (the first tab is clicked if another is selected). Also hidden: compose buttons and the reply box under an opened post (`iroha-x-composer`), Grok (`/i/grok` links, `GrokDrawer`), and on each post the ⋯ menu (`caret`), repost (`retweet`/`unretweet`), share and Grok buttons (matched by aria-label), "Translate post" (each button is checked once, `data-iroha-t`) and verified badges. Each post's action bar gets a copy-link button where share was (`addShareButtons`, a slot appended to `[role=group]`): it sends `/user/status/id` (from the link around the post's `time`) to the `irohaShare` handler, and `BrowserModel.copyShareLink` copies it on `XScripts.shareHost` (girlcockx.com by default; fxtwitter, vxtwitter, fixupx or x.com from the X menu's コピーするリンク) and shows a toast. `tidyActions` hides an action-bar slot holding only hidden buttons (`iroha-x-gone`), so the rest spread without gaps. A post is a translation (hidden, unless the label names Korean or Chinese) when X's label (翻訳, Translated from, 原文を表示…) appears anywhere in it, including inside the text block, or when its `lang` is a foreign one while the text shown is Japanese.
- **Page scripts are Swift string literals, so Swift escapes apply.** A `\n` written inside a JS string in a `"""` literal becomes a real line break in the page, which is a syntax error that silently kills the whole script (this disabled every X change for two rounds). Write `\\n`, and likewise `\\/`, `\\d` in regexes: Swift rejects escapes it doesn't know ("invalid escape sequence"). Run `python3 tools/check-page-scripts.py` after touching one: it flags escapes Swift won't accept and runs node `--check` on every embedded script.
- **Links from other apps** (`Service/OpenInIroha`): iOS lets only x.com/youtube.com themselves choose an app for their links, so いろは can't take them over. Instead there is the App Intent いろはで開く (`OpenInIrohaIntent`, opens the app; usable from a share-sheet shortcut) and `donguri://open?url=…`; both go through `AppNavigator.openInBrowser`, so X posts land in the X tab and YouTube in the player. The intent is a plain struct with a `@MainActor perform` (`nonisolated` on it fails: it has a stored `@Parameter`); the shortcuts provider is `nonisolated`.
- **興味なし** (long press or swipe a feed row, long press in 次の動画): `YouTubeFeedModel.markNotInterested` drops the video from every cached tab at once and remembers its id (`iroha.youtube.notInterested`, last 1000) so feeds and search keep it out; signed in, it also sends YouTube's own feedback (`YouTubeClient.markNotInterested`, `feedback` with the token from the video's menu), so recommendations learn. `YTParse.notInterestedToken` finds the token in old renderers (`menuServiceItemRenderer` with the NOT_INTERESTED icon) and in lockups (a `listItemViewModel` by icon or title 興味なし / Not interested).
